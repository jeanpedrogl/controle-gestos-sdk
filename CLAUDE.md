# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The computer-side half of a two-part system to fly a **DJI Mini SE** by hand gestures seen by the **drone's own camera** (the phone relays its video; the computer's webcam is not used). The other half is the Android app **Drone Bridge** at `../drone-bridge` (`/home/jean/projetos/drone-bridge`), which is a dumb bridge: it has no vision logic, it just forwards ROS2 commands from here to the DJI SDK and streams the drone's own camera back for monitoring. See that project's `CLAUDE.md` for the Android/DJI side, and its `PROTOCOLO.md` / `MANUAL_DESENVOLVEDOR.md` for the contract and the mandatory safety rules for any computer-side program (this package follows them).

This is a ROS2 **Humble** `ament_python` workspace (`colcon build`), not a plain Python script collection — the entry points are ROS2 nodes, run via `ros2 launch`, not `python foo.py`.

## Why ROS2 + rosbridge instead of ROS2-native on both ends

Android has no `rclpy`/`rclcpp`. The phone talks to this computer over a WebSocket using the rosbridge JSON protocol (`rosbridge_suite`, `ros-humble-rosbridge-suite`), which bridges to genuine ROS2 topics. From this package's point of view the phone is just another ROS2 node — publish/subscribe normally, rosbridge handles the translation. Don't try to add a native Android ROS2 client; it doesn't exist for this SDK generation.

## Build / run

```bash
./setup_ambiente.sh          # once: installs ROS2 Humble + rosbridge-suite (apt, needs sudo) + a --system-site-packages venv with mediapipe/opencv/numpy/matplotlib
source /opt/ros/humble/setup.bash
source .venv/bin/activate
python3 -m colcon build --symlink-install
source install/setup.bash
ros2 launch ponte_visao_drone sistema.launch.py
```

- The venv **must** be created with `--system-site-packages` — `rclpy` comes from the apt-installed ROS2, not pip, and a normal venv would hide it.
- **Build with `python3 -m colcon build`, never bare `colcon build`.** The apt-installed `colcon` executable has its own hardcoded `#!/usr/bin/python3` shebang, so invoking it directly ignores whatever venv is active — the generated `install/.../lib/ponte_visao_drone/piloto_gestos` entry-point script ends up shebanged to the *system* Python too, which can't see `mediapipe` (pip-installed only in `.venv`), and the node dies with `ModuleNotFoundError: No module named 'mediapipe'` at launch. Running colcon as a module (`python3 -m colcon ...`) under the activated venv's `python3` makes `sys.executable` (and so the generated shebang) correctly point at `.venv/bin/python3`. If a build was ever done the wrong way, `rm -rf build install log` before rebuilding — stale generated scripts don't get their shebang fixed by a later `--symlink-install` rebuild alone.
- **`matplotlib` must be pip-installed into `.venv` itself, not left to the system package.** `mediapipe.tasks.python.vision` eagerly imports `drawing_utils`, which imports `matplotlib` — unrelated to anything this project actually plots, but the import happens regardless. Because the venv is `--system-site-packages`, `pip install -r requirements.txt` sees Ubuntu's `python3-matplotlib` (apt, compiled against numpy 1.x) as "already satisfied" and skips it — but `mediapipe`/`opencv-python` pull in numpy 2.x, and the numpy-1-ABI-compiled system matplotlib then crashes on import (`AttributeError: _ARRAY_API not found`). Downgrading numpy instead just moves the break to `opencv-python` (it hard-requires numpy>=2). The fix is `pip install --force-reinstall matplotlib` inside the venv: a fresh numpy-2-compatible wheel lands in `.venv/lib/python3.10/site-packages`, which comes before the system `dist-packages` on `sys.path`, so it shadows the incompatible one. `setup_ambiente.sh` does this automatically; if dependencies ever get reinstalled by hand, redo that step too.
- `setup_ambiente.sh` is idempotent: it skips the ROS2/apt install if `ros2` is already on `PATH`.
- `controle-visao-v3` was created by copying the original `controle-visao` folder, including `.venv`, `build/` and `install/`, which kept the old absolute paths (so a build would have run the other folder's code). `.venv/bin/*` were repointed with `sed` and `build install log` were regenerated. If a similar copy is ever made again: fix `.venv/bin/*` paths (or recreate the venv with `setup_ambiente.sh`), then `rm -rf build install log` and rebuild.
- Quick sanity check of the pose classifier without ROS2 or a drone (uses the computer's webcam, only for debugging the poses; run it from `src/ponte_visao_drone`): `.venv/bin/python -m ponte_visao_drone.visao_mao`.

## Architecture

- `poses_mao.py`: **pure** (numpy only) static-pose classifier: 21 landmarks → `Gesto` (`classificar_pose`). Gestures are poses held, never movements (the old drag/palm-size-motion gestures are gone): index up/down, fist + thumb left/right, V (always counter-clockwise yaw), hang loose, open hand fingers-up, fist (thumb tucked). More than one hand in the frame is `VARIAS_MAOS` (`classificar_maos`; the detector runs with `num_hands=2`): no command at all, so a bystander in the drone's view can't take over (it also blocks the owner's own two hands). The fist ("mão fechada") needs all four fingers folded and the thumb tucked: thumb tip at most `POLEGAR_FORA_MAX` (0.15 palm) outside the bounding box of the other hand points (`polegar_fora_da_mao`) *and* under `FATOR_POLEGAR_RECOLHIDO` (0.85 palm) from the palm centre — calibrated on a labelled webcam recording (fists vs thumb gestures): the old rule (centre distance < 0.5, no box) rejected ~1/3 of real fists (64% → 95% of frames), with the same isolated false positives on thumb gestures. Anything else, including a thumb up/down or crooked thumb, is `DESCONHECIDO` (hover) — a crooked thumb must never count as a fist because the fist takes off or lands. Thresholds (`FATOR_*`, `LIMIAR_*`) were never tried on a real hand; the open-hand gesture does not check palm vs back of hand. Tested with synthetic hands in `test/test_poses_mao.py`.
- `visao_mao.py`: MediaPipe wrapper (`DetectorGestos`), **two-stage**: `PoseLandmarker` (VIDEO mode, `num_poses=2`, model `pose_landmarker_full.task`) on the whole frame finds the person; `recorte_mao.recortes_maos` turns the pose into square crops of the raised hands, taken from the full-resolution frame (`cv2.getRectSubPix`, resized to 256); `HandLandmarker` (IMAGE mode, because the crop moves) runs only on those crops and the landmarks are mapped back to frame pixels. Two people → `VARIAS_PESSOAS`; no person, or a person without visible shoulders (`recortes_maos` returns None: hand close to the camera) → fallback to `HandLandmarker` on the whole frame (old behaviour). Exposes `maos`, `corpos`, `recortes`, `modo` for the HUD (`desenhar`). `frames_confirmacao`-frame stabilization — 3 by default, 2 in the pilot. Plus the webcam demo, which runs the same two stages. No ROS2, no drone semantics. Cost on the dev laptop (Ryzen 5 2500U, CPU only): pose ~46 ms + ~45 ms per hand crop (the HandLandmarker always reruns its palm detector in IMAGE mode).
- `recorte_mao.py`: **pure** (numpy only): which raised hands to crop from the 33 pose points (wrist above mid-torso; mid-torso from the hips, or 1.5 shoulder widths below the shoulders when hips are hidden), crop centre (between pose index/pinky, else forearm extension), side 1.1 shoulder widths (min 48 px), `para_quadro` mapping and `remover_duplicadas`. Tested in `test/test_recorte_mao.py`.
- `comando_voo.py`: **pure** logic (no ROS, no webcam, no MediaPipe — gestures come in by `Gesto.name`): gesture→`(x,y,z,yaw)` mapping, speed constants (`VELOCIDADE_*` = 0.2 of the app's limits), and `Suavizador` (ramps: 0.3 s up, 0.15 s down, sign flips pass through zero). Unit-tested in `test/test_comando_voo.py` (`python3 -m pytest test/test_comando_voo.py`, no venv needed). Put anything that turns input into numbers here.
- `integracao_visao_drone.py`: the `piloto_gestos` ROS2 node. The frames come from the drone camera, not a webcam: `_ao_video` (executor thread) only stores the latest JPEG from `/phone/drone_camera/compressed` (best-effort, depth 1); the main-thread loop takes the newest one with `quadro_novo()`, decodes it, mirrors it (`cv2.flip`) and calls `DetectorGestos.processar()` / `definir_gesto()` / `avaliar_punho()` with the frame's *arrival* time, so the gesture age includes the video latency; the HUD is redrawn every loop and says "SEM VIDEO" after 1 s without frames; a `SingleThreadedExecutor` spins the node in a background thread so the 20 Hz timer (`_passo`, publishes `/drone/cmd_vel`), the `/phone/telemetria` and `/phone/rpc/response` callbacks never depend on the webcam rate (state is guarded by an `RLock`). It follows the Drone Bridge safety rules: starts disarmed (`a` key); arming needs fresh telemetry, `drone_conectado` and a subscriber on `/drone/stick_mode`; a stale gesture (>0.6 s, `GESTO_VALIDO_S`: the relay is ~8 fps and the phone drops frames when the Wi-Fi lags) publishes zeros, and the fist-landing countdown restarts if the video stalls mid-count; telemetry `stick_mode:false` after a 3 s grace or lost telemetry disarms and never re-arms; every exit path (`q`, Ctrl+C, SIGTERM, exception, webcam failure) goes through `desarmar()` (zero Twist, then `stick_mode:false`) in `main()`'s `finally`. `rclpy.init(signal_handler_options=SignalHandlerOptions.NO)` is required on Humble, otherwise Ctrl+C invalidates the context before the disarm can publish. Takeoff/land go over RPC (`flight.take_off`/`flight.land`, unique ids, answer shown in the window), not the fire-and-forget `/drone/takeoff`/`/drone/land` topics; the fist held 2 s (`avaliar_punho`, once per fist: it must be released first; non-fist gaps up to `TOLERANCIA_PUNHO_S` = 0.4 s neither reset the countdown nor count as a release; the HUD shows the countdown) takes off if telemetry says `voando` is false and lands if true (nothing without telemetry); takeoff by gesture additionally needs the program armed (`a`) — landing never does, the key `t` is unchanged; a takeoff already requested is not repeated for 10 s, except that an error reply to `flight.take_off` frees a retry (unverified on hardware: whether `flight.take_off` is accepted while stick mode is on); keys `1`-`4` send `video.set_quality` with `PRESETS_VIDEO` (the reply's effective values are shown in the HUD; the numbers are initial guesses to tune in the field); `t` needs a second press within 3 s and takeoff refuses with no telemetry, no drone or when already flying. There is no `camera_index` any more.
- `visor_camera_drone.py`: the `visor_camera_drone` ROS2 node. Subscribes to the drone video the phone relays and shows it in an OpenCV window. Pure monitoring — never touches control. No longer started by `sistema.launch.py` (the pilot window already shows this video); run it by hand with `ros2 run` if wanted.
- Axis convention is **REP 103** (x=forward, y=left, z=up, yaw+=counter-clockwise) on the `Twist` messages published here. The phone is responsible for converting this into whatever sign/axis convention the DJI SDK's `FlightControlData` actually wants (that SDK has its own well-documented pitch/roll-swap quirk — see `drone-bridge`'s `CLAUDE.md`). Don't "fix" the convention here to match DJI directly; keep this side ROS-idiomatic so other ROS tooling/nodes added later aren't surprised.
- Topic contract (publishers here → phone subscribes; phone publishes → nodes here subscribe) is documented in `README.md`. It's deliberately plain topics with standard or `std_msgs/String`-JSON payloads (no custom `.msg` package) so extending it later (new command, new telemetry field) never requires a `colcon` message-generation round trip — just start publishing/subscribing the new topic from either side.

## Non-obvious pitfalls

- `rosbridge_server`'s ROS2 port works with arbitrary message types via `rosidl` introspection — it is not limited to a fixed allowlist, so new topic types "just work" through the bridge without extra configuration on either end.
- `sensor_msgs/CompressedImage.data` arrives in this process as a normal `bytes`-like array (`uint8[]`) — rosbridge already decodes the base64 the phone sends over the WebSocket before it reaches this ROS2 node. Don't re-base64-decode it here.
- The hand-tracking model (`ponte_visao_drone/modelos/hand_landmarker.task`) is bundled, but `DetectorGestos.__init__` also auto-downloads it if missing — don't remove that fallback, it's what makes a fresh checkout runnable without manually fetching the model.
- Ctrl+C inside `ros2 launch` delivers **two** SIGINTs to each node (the terminal signals the whole process group and launch forwards it again). `piloto_gestos` installs `_encerrar` for SIGINT/SIGTERM, which ignores later signals so a second one can't interrupt `desarmar()` in the `finally` (without it the node segfaulted on exit under launch). `visor_camera_drone` does the same around its cleanup.
- `rclpy` loggers reject different severities from the same call site (`getattr(logger, level)(...)` raises `ValueError`); keep distinct `log.info/warning/error` lines, as `_avisar` does.
- OpenCV `putText` cannot draw accented characters — HUD strings are ASCII on purpose.
- Hardware behavior (whether the chosen axis signs/speeds actually feel right on a real aircraft, Wi-Fi hotspot range/latency between phone and computer in the field) has not been verified — this has only been exercised against synthetic/webcam input so far.
- **Drone-camera vision: decisions and open problems.** Decided: the V gesture is a single counter-clockwise yaw (the camera turns with the drone, so picking the direction from the hand's side of the image would make a centring servo that chatters); there is no clockwise yaw gesture. Forward (hang loose, x+) flies the drone *towards the person making the gestures*, so it runs at half speed (`FATOR_FRENTE = 0.5` in `comando_voo.py`: 0.4 m/s); backward (open hand) is still full 0.8 m/s. Now handled: the hand-too-small problem (the drone camera is wide-angle, so MediaPipe's full-frame palm detector only found the hand ~20 cm away in field tests) via the two-stage detector above; its range, the pose-crop geometry constants and the 8 fps budget are unverified on hardware. Lateral is also in the person's frame: since the drone faces the person, thumb right (the person's right) publishes `y+` (the drone's left) and thumb left `y-` — the opposite of v2, where the drone faced away from the pilot. Open: (1) Video latency (phone re-encode + Wi-Fi) is unmeasured; the relay can be raised with `video.set_quality` (not done automatically). (2) The gimbal pitch is not managed, so the user must stay in frame.
